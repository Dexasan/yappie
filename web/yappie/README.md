# Yappie website and email handoff

The public site is hosted by the `yappie-public` Cloudflare Worker at
[yappie.site](https://yappie.site). Source assets are copies of the approved
Yappie artwork. The home page is the entry point for browser chat. Add the
Android install link to `public/index.html` when the app is publicly released.
The privacy and support pages are for the Android beta; a formal privacy contact
is still needed before a public store launch.

Search visibility setup, confirmed Google/Bing submissions, and the free
IndexNow update command are recorded in
[the search visibility record](../../docs/YAPPIE_SEARCH_VISIBILITY.md).

From the repository root, with Wrangler authenticated to the Cloudflare account
that owns the zone:

```powershell
pnpm dlx wrangler deploy --config web/yappie/wrangler.jsonc --dry-run
pnpm dlx wrangler deploy --config web/yappie/wrangler.jsonc
```

The email routes accept an encoded `ConfirmationURL` from the email after an
explicit click and preserve the installed APK's PKCE handoff. Don't add analytics
to the email routes or log their request bodies, email fragments, upstream URLs,
or redirect codes. Preserve the current Supabase mobile callback allowlist.

The Supabase email HTML is generated by `node scripts/render-auth-emails.cjs`.
Deploy the Worker and confirm its HTTPS endpoints before saving changes to the
live templates. For rollout and rollback details, see
[the auth email setup record](../../docs/AUTH_EMAIL_SETUP.md).

## Web chat beta

### Community sticky-note wall

The matching page has a shared wall with 20 note slots, split between the black
desktop margins. Below 1000px it becomes an expandable wall beneath matching.
It is hidden during conversations and excluded from the embedded Android page.
Paper colours reuse the chalk, coral, sage and lilac palette; the SVG uses the
original `InkArtwork.tsx` note silhouette. No generated example notes are added.

Notes accept 1–9 whitespace-separated words and at most 120 characters, with
matching normalization/validation in the browser and Worker. Text is rendered
with text nodes; only explicit HTTP(S) links become anchors, with
`noopener noreferrer nofollow ugc`. A note can be placed in a chosen empty slot
or the next available slot. The posting form identifies the text as public and
requires the 18+/chat-rules acknowledgement.

`STICKY_WALL` / `StickyWall` is a separate SQLite Durable Object, with an additive
`sticky-wall-v1` migration. Notes persist across page loads and deployments;
they do not expire automatically. Reads expose only public note data, capacity,
occupancy, revision and removal eligibility. No guest chat/session is required.
The client polls at 15-second intervals only while the wall is visible; a closed
mobile wall, background tab and active conversation do not keep polling.

Public removal is enabled when the current count is at least 12/20 (60%). A
single storage transaction checks that threshold and removes the selected note.
At 12, one successful removal takes the wall to 11 and locks removals again.
It applies equally to all notes, with no ownership privilege. The client waits
for the server, then animates deleted paper falling below the viewport, including
notes removed by other visitors between polls. Reduced-motion preferences skip
the falling animation. Revision checks prevent older responses restoring notes.
Posting uses a stable request ID so retries cannot duplicate a note, and slot
conflicts/full walls retain the draft with an actionable error.

Daily wall-specific network HMACs enforce 3 posts, 30 removals and 10 reports per
hour per network. These are separate from the chat and visitor-counter keys.
Rate-limit rows expire after one hour. Anyone can report a note at any occupancy;
reports retain its text, reason and protected moderation identifiers for up to
30 days. Alarm cleanup handles expiry even without subsequent visitors. The
public API never exposes protected network identifiers, reports or credentials.

Moderators can read `GET /wall-api/moderation` using the existing moderator bearer
token. `POST` to that endpoint with `{"action":"remove","id":"NOTE_UUID"}`
removes a note at any occupancy and marks its reports reviewed. Keep the token
private. No dedicated new moderator screen or paid service is introduced.

Validated and deployed on 25 November 2026. Run
`node scripts/verify-sticky-wall.cjs` for seven SQLite-backed protocol checks:
persistence/retries, text/age/payload limits, origin/method checks, atomic
12-to-11 removal locking, concurrent slot claims/full capacity, hourly posting
limits, and private moderation/report expiry. The seven visitor-counter checks
and ten shared-chat checks also passed. Wrangler's deployment dry run passed.

Browser QA used the local Worker at 320px, 390px, 1000px and 1366px. It covered

No browser console errors were observed. Test notes remain in local QA storage

### Public five-second visit counter

The matching header shows **Visits**. Each page load counts once after five
visible seconds, without needing a click, window focus, cookies, browser
identification or a sign-up. Hidden-tab time pauses the timer. Refreshes,
return visits and separate tabs can count again: this is a visit total, not a
unique-human or online-user count. Script-capable bots can qualify too. No
arbitrary number or historical Cloudflare total is added.

The root (including its closed-chat fallback) and public help pages load
`/visitor-counter.js`; auth routes and the embedded Android entry are excluded.
Matching does not depend on counting. The client requests a signed page token
and automatically commits after five visible seconds. The Worker checks the
same-origin JSON request, signature and minimum five-second proof age. A
storage transaction deduplicates that page token so concurrent network retries
increment once. No per-browser or per-network lifetime limit is applied.

The counter creates no cookies and retains no IP addresses, user agents,
account identifiers, referrers or chat content. Only short-lived random page
tokens prevent duplicate requests; expired records are removed during later
registrations. A blocked request or disabled JavaScript can miss a visit.
Aggregate totals persist across deployments. Legacy cookie/network rows from
the earlier engaged-browser counter no longer affect counting and retain their
expiry cleanup. The old visitor cookie is ignored.

The binding and additive migration are in `wrangler.jsonc`; the existing chat
object and its migration are preserved. Signing uses the existing
`WEB_CHAT_SECRET` with separate HMAC contexts. No new provider, paid plan or
credentials are required. SQLite Durable Objects are available on Workers Free;
free quota exhaustion fails requests instead of buying extra capacity. Keep the
account on its Free plan for the owner's zero-euro budget. See Cloudflare's
[Durable Objects pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/).

The owner requested simpler counting and deployment on 23 November 2026.
`node scripts/verify-visitor-counter.cjs` passes five-second timing, cookie-free
counting, return visits, persistence, concurrent/replayed commit idempotency,
forged/expired proof rejection, malformed bodies, cross-origin rejection and
storage failures. A browser-script test confirms automatic registration with
no click/focus/cookie requirements, hidden-tab timer pausing and one commit per
page. The previously verified 320/390px counter layout is preserved with the
shorter label. Local Wrangler previews need `--infer-origin-from-routes=false`.

## Shared website and Android matching

The Android interest picker opens `/chat-app` in an in-app WebView. That entry
point verifies the account's Supabase session, completed age-verified profile,
policy acknowledgements, languages, and block list. It then establishes a
temporary HttpOnly cookie using a private, stable account identifier. Access
tokens travel in request headers and are never added to the page or URL.
Only two verified app accounts receive each other's profile reference, allowing
the native **Follow + save** control to keep their connection. Browser guests
receive no app profile reference.

Both platforms use the existing `WEB_CHAT_POOL.getByName('web-v1')` Durable
Object for matching, text delivery, voice signaling, and stranger-chat reports.
Android passes its existing 1–5 selected interests. Browser visitors can select
a chat language. Matching prefers shared interests and only falls back when
neither person has an eligible shared-interest partner waiting.

The app retains discovery personalization through
`remember_quick_chat_interests`, which does not join the legacy SQL queue.
Moderators can open **Me → Review reports → Stranger chat reports** to review
reported excerpts from both platforms. The Worker verifies their moderator role
on each request and records review/network-limit actions in the shared pool.

Roll out the pending SQL migrations and updated Worker before distributing the
new Android build. Existing installed APKs use the SQL matcher until updated.
The new app uses the common pool exclusively. Native-to-native, native-to-browser,
and browser-to-browser matching, microphone permission, voice teardown, account
blocks, reporting, and disconnect/reconnect behavior require the combined
validation pass and physical Android/browser checks before release.
